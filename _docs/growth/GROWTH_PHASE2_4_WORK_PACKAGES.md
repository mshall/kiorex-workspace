## 1. Cross-cutting rules for every package in this file

1. **Additive only.** No existing column, enum value, event field or endpoint changes meaning. New columns nullable or defaulted. Flags default per ADR-023: engine pieces `ON` in dev and staging, anything that sends marketing, issues or redeems money, runs the WhatsApp model, collects visitor analytics, or touches corporate or loyalty is **launch-locked** (needs a human-recorded gate in the Super Admin, never recorded by code).
2. **No PHI in growth.** Specialty, doctor, visit reason, diagnosis, prescription, lab or pharmacy contents never join a growth identity, an ad payload, a segment or a model prompt. Existing `growth-no-phi.unit.spec.ts` is extended per package; `no-health-targeting.unit.spec.ts` (ARCH 14) lands in P2-F and covers every new module.
3. **Money paths are append-only and idempotent** (ledger entries, decisions, spend approvals). Two-person rule on every configuration that moves money or messaging (existing `GrowthConfigVersion` maker-checker).
4. **Mock-first, config-only real.** Every adapter has `mode: mock | real`; real mode needs `secretRef` names (validated `^[a-z0-9/_-]+$`) and is never exercised in CI.
5. **AR and EN, RTL, tokens.** Every UI string in both languages in the namespaced i18n file of the package, Arabic default in Egypt, Arabic-Indic digits via the existing formatter, brand tokens (`_brand`), `prefers-reduced-motion`, 44 px touch targets, 320 px to 2560 px layout check in Playwright.
6. **Tests named like existing ones.** KP: `*.unit.spec.ts`, `test/*.int.spec.ts`; CM: `*.node.test.ts`, `*.integration.test.ts`; KC, KA, KL: vitest or jest as today. E2E suites continue the numbering: `29` to `39` are reserved here (section 12).
7. **Each package ends with:** unit and integration tests green, lint and typecheck green, OpenAPI regenerated (`openapi-export.ts` in KP, `openapi:export` in CM) and `Docs/API.md` regenerated, `Docs/GROWTH.md` section, flag documented, `Docs/NEEDS_HUMAN.md` row updated if a gate or placeholder is introduced, requirement id in the Conventional Commit, no secret or build output in git.
8. **Retention and erasure.** Every new table that holds a `sub` or a hash derived from a person is registered with `growth_erase_subject` (extend the SQL function in that wave's migration, never edit an old one), and with `growth_purge_expired` (new retention arguments added through a new function version `growth_purge_expired_v2`).
9. **Observability.** Every job writes a heartbeat row (`GrowthJobRun`, created in X1) and increments the existing job metrics; every package adds its SLIs to `Docs/GROWTH.md` section "SLOs" (ARCH 20 pattern).

## 4. Strategies applying to all waves

### 4.1 Parallelisation rules

At most four agents per wave. Each agent owns a repo-and-folder set listed in the wave tables; if two packages must touch one file the single owner of section 2 does it. An agent that finishes early takes only **tests, docs or Playwright for its own package**, never another agent's folder. Agents commit in small Conventional Commits with the package id (`feat(growth): GRW-P2-A campaign state machine`), `Co-Authored-By` trailer, no push.

### 4.2 Contract versioning plan

See 0.2. The order inside a wave is fixed: contracts first (X0 or the wave's contract task), tarball vendored, **then** schema, **then** services, **then** UI. A package never depends on an unreleased contract; if it needs a field that is missing it requests a patch release (1.12.1) from the contract owner.

### 4.3 Migration ordering plan (avoid out-of-order names)

Rule: a migration directory name (`YYYYMMDDHHMMSS_name`) must sort strictly after every migration already on `main` of that repo at merge time, and each wave reserves a **numeric block** so concurrent agents cannot interleave. Slots below are reserved; they intentionally use calendar-looking prefixes after the latest names observed (KP `20261130090000_growth_link_registry`; CM `20261201090000_shared_rate_limit_and_nonce`; PH and LB latest `20261126120000_*` pattern, CONFIRM AT START with `ls prisma/migrations | tail`). If a hotfix migration lands first with a later name, the schema owner renames its own (unmerged) directory to the next free second inside the block before merging; never edit a merged migration; never reuse a name.

Full cancel before completion: credit +150 restored, card 250 to original (or +250 `REFUND_CREDIT`), sponsored 100 released, patient total back 400 = C + K. ### GRW-P2-S Provider-sponsored promotions (CM, KP, KC fixtures, A2, 14 days; W7 because it needs B2 checkout lines and P2-W wallet methods from W6)
Status: founder decision of 24 Nov 2026, Proposed (ADR-048, KX-30 section 14). **A provider-sponsored promotion is a discount the clinic funds, not a conversion of balances.** The patient never receives provider credit, the clinic never receives patient credit, and no ledger entry in one system names an object in the other; the only link is a promotion expense line that refers to a booking. Locked behind `growth.sponsored_promotions` (counsel on advertising and accounting for production, H-26, H-28).
- **Ownership.** The promotion is a **provider-owned asset (ADR-041)**: it is configured in the Clinic, the budget and the wallet are in the Clinic, and the Kiorex marketplace receives a signed projection to quote and display it. Kiorex ops reviews content and scope; the Clinic debits the wallet.
- **Promotion model (CM, migration `20270107120000_growth_sponsored_promotions`, additive).** `SponsoredPromotion(id, tenantId, status DRAFT|SUBMITTED|IN_REVIEW|APPROVED|ACTIVE|PAUSED|EXHAUSTED|EXPIRED|REJECTED|ARCHIVED, currentVersionId, createdBy, createdAt)`; `SponsoredPromotionVersion(id, promotionId, version, name{ar,en}, patientCopy{ar,en}, scope {doctorIds[], appointmentTypeIds[], careTypes (IN_CLINIC|VIDEO|HOME_VISIT)}, discount {kind FIXED_MINOR|PERCENT_BP, value, maxPerBookingMinor}, budgetCapMinor, perPatientLimit, perDayLimit?, eligibility {newPatientsOnly, firstBookingOnly, minLeadHours, kiorexOnly}, startsAt, endsAt, fundingMode WALLET_ONLY|WALLET_THEN_INVOICE, policyVersion, referencePriceMinor (snapshot for the inflation check), contentHash)` immutable (an edit creates a new version, bookings cite the version they used); `PromotionComplianceReview(id, versionId, kind CONTENT|SCOPE|HIGH_VALUE, requestedBy, decidedBy?, decision?, reason?, CHECK decidedBy <> requestedBy)`; `PromotionBudgetEntry(id, promotionId, versionId, type RESERVE|RELEASE|DEBIT|REVERSE_DEBIT, amountMinor, currency, idempotencyKey unique, appointmentId?, bookingRef?, walletEntryId?, invoiceLineId?, reason, createdAt)` append-only with the W-5 style trigger and a deferred constraint that refuses `reserved + debited - released - reversed > budgetCap` (race-proof, `FOR UPDATE` on the promotion row); `PromotionAudit(id, promotionId, actor, action, snapshot jsonb, at)`.
- **Eligibility and scope rules (code and test).** Scope only by the clinic's own doctors, appointment types and care type; eligibility only non-clinical (new to this clinic, first Kiorex booking, time window, lead time); **no health targeting, no diagnosis, drug, procedure, test or treatment in scope or copy; the discount applies to the visit fee component only (consultation, follow-up, video, home visit fee), never to a prescription, test or procedure**; one sponsored promotion per booking (no promotion stacking), stacking with patient credit allowed (credit applies after, B2 lines); a promotion can be paused by the clinic at any time, never edited in place, a budget increase is a new version and a new review.
- **Advertising compliance and review (human and code).** Every version goes to `IN_REVIEW`: automated `content-guard` (banned phrase list, no clinical claims, no "free treatment" inducement, AR and EN, no superlatives about outcomes) then a human reviewer in Kiorex ops (Super Admin or a `GROWTH_ADMIN` role). **High value** (budget cap at or above `highValueBudgetMinor`, or per-booking discount at or above `highValuePerBookingMinor`, or percent above `maxDiscountBp`, thresholds in `SPONSORED_PROMOTION_POLICY`) needs a **second approver (maker-checker, author and approver differ, enforced by CHECK and by the config version rule)**; the decision travels as `PromotionReviewDecided` (Kiorex to Clinic). Patient surfaces always show "Discount sponsored by <clinic name>" and the end date; the promotion is never presented as a Kiorex discount. Egyptian medical-advertising rules are a human item (H-28); until then the guard list is a placeholder.
- **Booking-time reservation (budget hold).** Kiorex quote finds the single best eligible active promotion for the chosen doctor and service and shows the line. At hold or booking time Kiorex calls the Clinic, signed like every marketplace command, `POST /marketplace/v1/promotions/{id}/reserve {version, bookingRef, patientRef (opaque keyed hash, never the `sub`), careType, amountMinor, currency, idempotencyKey}`; the Clinic re-checks status, window, eligibility, per-patient limit and **writes a RESERVE entry against the budget cap**; with `WALLET_ONLY` it also requires `walletAvailable - openReservations >= amount` (a reservation is a budget hold, the wallet is not touched yet); with `WALLET_THEN_INVOICE` a shortfall is allowed and will be invoiced; reply `{reservationRef, expiresAt}` or a reason (`BUDGET_EXHAUSTED`, `NOT_ELIGIBLE`, `PAUSED`, `WALLET_INSUFFICIENT`, `LIMIT_REACHED`). The reservation expires with the hold (TTL equals hold TTL plus a grace) and a sweeper writes RELEASE. The confirmed booking call carries the optional `sponsoredDiscount {promotionId, promotionVersion, reservationRef, amountMinor, currency}` block (contracts 1.12.0).
- **Completion debit.** When the visit is attended and completed (the same attendance evidence as the commission charge: check-in, then COMPLETED or 24 h CONFIRMED) the Clinic writes DEBIT: `CreditWalletService.consume(tenant, amount, SPONSORED_PROMOTION, {sourceRef: promo:<promotionId>:<appointmentId>, idempotencyKey})` inside one transaction with the DEBIT entry, then emits `SponsoredDiscountDebited` to Kiorex. If the wallet is insufficient and the funding mode allows, the shortfall becomes an invoice line `PROMOTION_EXPENSE` on the next Kiorly invoice (new line kind in `kiorly-invoices.service.ts`). **The sponsored part of the deposit payout is released to the clinic only after the DEBIT exists** (Kiorex Pay payout eligibility check on the sponsored line state).
- **Cancel, refund, no-show, reversal.** Cancelled or expired before completion: RELEASE (budget freed, wallet untouched). No-show or deposit forfeited: RELEASE (no discount was earned). Refunded or disputed after completion inside the refund window: REVERSE_DEBIT and a wallet GRANT `SPONSORED_PROMOTION_REVERSAL` (idempotent), `SponsoredDiscountReversed` to Kiorex; the patient's refund follows B2 allocation (the sponsored share is voided, never paid out to the patient).
- **Money flow, explicit (documented in KX-09 section 06).** Example: visit deposit D 500, sponsored S 100, patient credit C 150 (Kiorex-funded), card K 250. At checkout the patient pays 250 by card; Kiorex Pay holds the deposit for the clinic as today. At completion Kiorex Pay pays the clinic the gross 500 (card 250 + platform-funded credit 150 + sponsor-funded 100); the clinic wallet is debited 100 (its funding of the discount). Net to the clinic is 400 in value, its fee commission is unchanged, and Kiorex has no revenue and no expense from S. The Kiorex booking ledger shows the lines `PRICE 500`, `PROVIDER_SPONSORED_DISCOUNT -100`, `PATIENT_CREDIT -150`, `CARD 250`; the clinic statement shows `Promotion expense (sponsored discounts) 100`. The settlement between the Kiorly wallet ledger and the Kiorex Pay held ledger is a daily reconciled accounting posting (`SPONSOR_FUNDED:clinicCredit -> deposit held`, written only when `REWARD_RULES.postToPayLedger` or the new `SPONSORED_PROMOTION_POLICY.postToPayLedger` is true; default false until finance decides, H-25).
- **Commission and revenue rule (versioned policy, config kind `SPONSORED_PROMOTION_POLICY`, maker-checker, effective at least 7 days after approval like every money policy).** `commissionBasis`: `GROSS_BEFORE_SPONSORED` (default) means the Kiorex fee is computed on the fee before any sponsored discount; `NET_AFTER_SPONSORED` is available for a future percentage-of-fee model only. Today the Kiorex fee is a flat amount per attended new patient (EGP 40, ADR-007), so the sponsored discount changes nothing about it; the rule is written so that a future percentage model has an explicit basis. The `KiorexCommissionDecision` and `COMMISSION_CHARGE_CREATED` carry `feeBasisMinor`, `sponsoredDiscountMinor` and `basisPolicyVersion` (additive, 1.12.0) so the decision is reproducible. **A sponsored promotion never changes chargeability or attribution** (a patient found through the marketplace stays `MARKETPLACE` and chargeable; a provider-led booking stays commission-free). **Kiorex revenue** stays commission plus Kiorex fees; the sponsored amount is provider-funded and is neither Kiorex revenue nor a Kiorex marketing expense; patient credit is never revenue (KX-32 definitions amended by P2-H).
- **Fraud checks (rule ids on `GrowthFraudSignal` and in the Clinic promotion audit, shadow first like AD-11):** `PF_SELF_DEAL` (patient phone or payment hash equals staff or owner hash of the clinic, via the P2-B1 staff-phone-match endpoint), `PF_FARM` (many accounts, one device or payment fingerprint, repeated first bookings), `PF_PRICE_INFLATION` (the clinic raised the visit fee or deposit within 30 days before or during the promotion compared with `referencePriceMinor`; blocks activation or flags), `PF_NO_ATTENDANCE` (debit never without attendance evidence; completion without check-in refused), `PF_VELOCITY` (budget burn rate beyond a multiple of plan), `PF_COLLUSION_LOOP` (same patients across promotions and clinics of related owners), `PF_CLINICAL_INDUCEMENT` (copy or scope keywords). Hold and review, never silently reduce a patient's discount after reservation.
- **Paths.** CM: `apps/api/src/promotions/{promotion.service.ts, promotion-version.ts, promotion-budget.service.ts (reserve, release, debit, reverse; pure `budgetState` in `promotion-budget-math.ts`), promotion-eligibility.ts, promotion-completion.consumer.ts (attendance and cancel events), promotion-reconcile.job.ts, promotion-fraud.rules.ts, promotions.controller.ts (clinic owner), promotions-marketplace.controller.ts (signed reserve and release), promotion-projection.publisher.ts (`PROVIDER_PROMOTION_UPDATED`), *.node.test.ts, *.integration.test.ts}`, edits in `kiorex/commission-decision.ts` and `kiorex-commission.service.ts` (basis fields), `billing-platform/kiorly-invoices.service.ts` (`PROMOTION_EXPENSE` line), `billing-platform/monthly-statement*.ts`, `marketplace/*` (booking intake reads `sponsoredDiscount`, validates reservation), web `apps/web/src/features/promotions/{PromotionsPage.tsx, PromotionWizard.tsx, PromotionBudgetCard.tsx, PromotionLedgerTable.tsx}` (AR and EN namespace `promotions.*`, budget, burn, reservations, debits, pause), staff app read-only status card.
