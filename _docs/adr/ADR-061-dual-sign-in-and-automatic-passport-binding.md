# ADR-061: Dual sign-in (Kiorex Passport and e-mail + password) and automatic Passport binding for every provider organisation

**Status: Accepted by the founder's instruction of 28 Nov 2026** (Lab passwords and the unified login were decided the same day). Extends ADR-038 (Kiorly Home, both methods always offered) and keeps ADR-059 and ADR-060 untouched.

## Decision
1. **Every provider organisation, standalone or connected, reaches Kiorex Passport without a manual step.** Passport itself already creates the identity from the first OTP-verified phone; this ADR defines how the PRODUCT user is bound to it:
   - **Self sign-up (Pharmacy)**: the sign-up answer carries a short-lived signed `ownerClaim` (20 minutes, own issuer and audience, not a session). The same browser continues with Kiorex Passport and sends the claim once with the code exchange. The owner row is bound to that Passport subject and its link phone becomes the phone Passport verified. Replay or another identity: `CLAIM_INVALID`; unverified phone: `PHONE_NOT_VERIFIED`; an identity already bound elsewhere: 409.
   - **Operator-created organisations (Lab `npm run org:create`, platform onboarding, seeds)** and **staff added by an owner or admin**: the phone recorded by an authorised person is the link key; with `OIDC_PHONE_LINK=true` the first Passport sign-in by the same OTP-verified phone binds the row (unique active match, audited `auth.passport_linked`).
   - **Clinic**: `KIOREX_PASSPORT_PHONE_LINK=true` does the same for exactly one active staff member whose `Employee.phone` equals the verified Passport phone (link kind `VERIFIED_PHONE`). Default OFF; the explicit password re-auth link stays.
   - Never from an unverified phone; never an identity created from product data; ownership checks and per-organisation isolation unchanged; the market stays fixed for life (ADR-060).
2. **Both sign-in options are offered when the server allows it**: new `AUTH_MODE=both` (Pharmacy, Lab) = Passport AND e-mail + password in a production-style process. The default stays `oidc` on hosted environments; the choice is per environment in the URL registry (`provider_sign_in`, `provider_phone_link`; the validator refuses `both` on prod).
3. **MFA policy is not weakened**: in `both` mode a password session never carries the MFA claim, so privileged roles (Pharmacy OWNER, PHARMACIST, BRANCH_MANAGER, CHAIN_OPS; Lab OWNER, LAB_DIRECTOR, AUTHORIZED_SIGNATORY, ...) are refused at password sign-in with `PASSPORT_REQUIRED_FOR_ROLE` and must use Passport (where the Passport MFA policy applies). Other roles sign in with a password. Sign-in limits: per e-mail and per client address (`SIGNIN_RATE_PER_MINUTE`, `SIGNIN_RATE_PER_IP_PER_MINUTE`), uniform failures; the Passport one-time-code limits are unchanged.
4. **Lab gets a real password model** (founder decision): scrypt hash (same format as the Pharmacy), minimum 10 characters, lockout after `LAB_LOGIN_LOCK_THRESHOLD` (5) wrong passwords for `LAB_LOGIN_LOCK_MINUTES` (15) with a uniform 401, change (current password), single-use e-mail reset (30 minutes, hashed token, mock messaging unless `EMAIL_MODE=real`), owner-set passwords on staff create and update, optional organisation slug (only needed when one e-mail exists in two organisations). Nothing is seeded or published.
5. **One unified login card** (`kiorex-account/packages/unified-login`) is vendored byte for byte into the Clinic, Pharmacy and Lab web apps (`scripts/sync-unified-login.sh`, parity tests in every repo). The server's `/auth/config` decides what shows. Kiorly Home's Password method now works for all three products wherever local login is enabled.

## Consequences and limits
- On kx-test an owner who never enrolled an authenticator still gets `403 MFA_REQUIRED` after a Passport sign-in without the second factor (unchanged). Recommended: turn the MFA policy on for organisation types pharmacy and lab before real owners arrive.
- A person with two organisations on one Passport cannot claim the second through the sign-up claim (refused as ambiguous); they are added by the second owner through the verified-phone link.
- Production sign-up of the Lab through Kiorex Account (NH-LB-016) is still not built: Lab organisations are created by the operator tool.
