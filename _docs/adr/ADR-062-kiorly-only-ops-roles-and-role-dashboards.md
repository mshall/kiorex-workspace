# ADR-062: Kiorly-only operations roles (kiorly_ops, kiorly_admin), separate accounts, and one dashboard per console role

**Status: Accepted by the founder's decision of 28 Nov 2026** (option A of `_docs/KIORLY_OPS_ROLE_SPLIT_DECISION.md`, recommended defaults, plus "every role has its own separate dashboard"). Extends ADR-059 (Kiorly admin is the Ops console on another host) and ADR-060 (Kiorly market launch stays `super_admin`).

## Decision
1. **Two new Passport roles.** `kiorly_ops`: read, review and onboarding actions on Kiorly data. `kiorly_admin`: everything `kiorly_ops` may do plus changes within the Kiorly scope (assign and export join requests, partner reject / go-live / pause / resume / rotation, enrolment codes, verification decisions). Kiorly market launch, commission maker and checker, and every price approval stay `super_admin`. A person may propose a plan price (the plans work lists those routes) and may never approve one.
2. **Only a `super_admin` grants or revokes them**, in Passport (Ops, Kiorly roles, `/account/ops/kiorly-roles`, API `/api/ops/kiorly-roles`), with a fresh MFA step-up, a reason of 3 to 300 characters, and a hash-chained audit entry (`kiorly.role.granted`, `kiorly.role.revoked`); every session of the person ends at once. MFA is mandatory for both roles exactly like `ops_admin` (baseline `mfaPolicy.requiredForRoles` in `config/idp.json`).
3. **Separate accounts.** A sign-in never holds Kiorex roles and Kiorly roles. Enforced at grant time (`409 mixed_roles` when the account holds anything other than `patient`; the grant replaces `patient`, the revoke puts it back; nobody grants themselves) AND in the API guard (a token that mixes a Kiorly role with any other role is refused everywhere with `403 FORBIDDEN_MIXED_ROLES`). The Kiorex console refuses a Kiorly-only sign-in with a clear message; the Kiorly console shows only the allowed views.
4. **Deny by default in the platform API.** For a token carrying a Kiorly role, an explicit allow-list (`apps/api/src/auth/kiorly-roles.ts`, `KIORLY_ALLOW`: method + route, level `ops` or `admin`) REPLACES the `@Roles` check; a route that is not listed, or that has no `@Roles`, answers `403 FORBIDDEN_ROLE`. A new route is therefore closed to these roles until someone lists it. Listed: provider directory, join requests, partner leads, partner onboarding and enrolments, verification updates, onboarding import batches (read only), commission policy and rate READ, fee statements, Kiorly markets READ, plans READ (plus the price-proposal routes added by the plans work), `GET /auth/me`. Refused on purpose: orders, finance, reconciliation, payments, messaging, integrations, flags, operations, outbox, bookings, moderation, growth, anything with patient identifiers, commission maker-checker, market launch, price approval. The test `apps/api/test/kiorly-roles.int.spec.ts` builds the route table of the running application and proves 403 on every unlisted route, reachability of every listed one, and the mixed-claims refusal; `ops-role-matrix.int.spec.ts` proves the console's access table never offers a route the API refuses.
5. **One dashboard per role in the Ops console** (`/home`): `super_admin` (approvals waiting across commission policy, rates, settings, flags, market change requests and partner approvals, audit highlights, system health links, Passport decisions linked), `ops_admin` (Kiorex operation queues), `finance` (commission claims, aging, disputes, reconciliation, matching queue, latest runs), `growth_admin` (growth KPIs), `kiorly_ops` and `kiorly_admin` (join requests with ages, onboarding queue and drafts, plans, markets, commission policy read; shortcuts for `kiorly_admin` only). Existing admin APIs only, counts and links, honest empty, error and no-access states, EN and AR with Western digits, light and dark. A person with several roles lands on the first by priority and can switch. The menu lists only routes the role may open (`apps/ops/src/lib/roleAccess.ts`); a hand-typed refused address shows a no-access page, and the API answers 403 to the same calls.

## Consequences and limits
- Row-level filtering by organisation type or market (the paper's phase 2) is NOT built: the Kiorly roles reach only routes that carry no patient identifiers, but shared lists (providers, join requests) are not filtered by product. Revisit only if Kiorly ops must also see finance or orders.
- The Ops sign-in client is still shared (`kiorex-ops`); the refusal of a Kiorly-only role on the Kiorex host is a console behaviour, the security boundary is the API guard.
- Cognito (production identity) needs no schema change: `custom:kx_roles` is a free comma-separated string (max 512) and the pre-token trigger passes it through; the grant screen belongs to the dev IdP that runs on kx-test, and the equivalent for Cognito (an admin API or group) is part of the production identity work. No `tofu` plan was needed or applied.
- A grant ends the person's sessions, so a live test that re-grants every run would cost phone codes: the test grants only when the role is not held yet.
